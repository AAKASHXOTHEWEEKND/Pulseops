# Security & Secrets

## Secret handling
- **No secrets in Git or images.** Config comes from environment variables; the DB password is generated by Terraform (`random_password`) and stored in **AWS Secrets Manager**. The full `DATABASE_URL` secret is injected into ECS tasks via the task definition `secrets` block — the value never appears in code, state as a literal, or the image. `.gitignore` blocks `.env` and `*.tfvars`; CI runs **gitleaks** on every PR.
- **Local**: docker-compose uses a default dev password via `POSTGRES_PASSWORD` (overridable in an un-committed `.env`). This is a local-only convenience, documented as such.

## Identity & least privilege
- **CI → AWS** uses **OIDC** (`aws-actions/configure-aws-credentials`) to assume a role for short-lived credentials — no long-lived AWS keys stored in GitHub.
- **ECS execution role** can pull images and read **only this app's** DB secret (resource-scoped `secretsmanager:GetSecretValue`), nothing else.
- **ECS task role** is separate from the execution role and currently minimal (extend per feature). Splitting them means the app's runtime identity can't read arbitrary secrets.

## Network boundaries
- Only the **ALB** is internet-facing. Web, API, worker, RDS, and Redis live in **private subnets** with no public IPs.
- RDS `publicly_accessible = false`; DB/Redis security groups accept traffic **only from the app security group** on their specific ports.

## Container hardening
- API/worker image runs as a **non-root** `app` user; web runs as **non-root** nginx (`nginxinc/nginx-unprivileged`).
- Multi-stage build → small runtime image; **pinned** dependencies (`requirements.txt`); `tini` as PID 1 for correct signal handling and zombie reaping.
- **Immutable image tags** (git SHA); ECR repos set to `IMMUTABLE` with `scan_on_push`.

## Dependency / container vulnerability handling
- CI builds the images and runs **Trivy** (HIGH/CRITICAL). Currently report-only (`exit-code: 0`) so a noisy base image doesn't block delivery on day one; flip to `exit-code: 1` once a baseline is triaged.
- ECR scan-on-push provides an ongoing registry-side scan.

## Secret rotation & revocation
- Rotate a leaked credential by updating the Secrets Manager value and restarting tasks (new tasks read the new value at start).
- Revoke CI access by removing the trust on the OIDC role — instant, no key hunting.

## Scenario: rotate the DB password without prolonged downtime
PostgreSQL supports multiple valid credentials during a transition, so rotate with **overlap**:
1. **Create a second credential**: add a new password (or a second DB role with identical grants). Both old and new now authenticate.
2. **Update the secret**: write the new `DATABASE_URL` into Secrets Manager as a new version.
3. **Rolling restart**: trigger a rolling ECS deploy (`deployment_minimum_healthy_percent = 100`). New tasks pick up the new secret; old tasks keep serving on the old credential until they drain — **no downtime**.
4. **Verify**: smoke test green; confirm new connections use the new credential.
5. **Retire the old credential**: once no task uses it, revoke/drop the old password.

Because the connection pool uses `pool_pre_ping`, stale connections are detected and replaced cleanly during the transition.

## Unacceptable patterns we avoid
No secrets in Git/images; no publicly accessible database; no long-lived admin keys in CI; no shared prod credentials; no running as root.
